# kjx-shopee-pipeline

> 1688 → Shopee 轻出海上货管道：七环全流程 + IP 判定 + Token 成本控制，沉淀成一个可复用的 Agent Skill。

一套跑通过的 **1688 货源 → Shopee 轻出海** 铺货管道，附带踩坑记录与判据。
本仓库**不含任何脚本**，只有方法论与规约——脚本由使用者按 `references/scripting.md` 的规约自行落地。

---

## 它解决什么

跨境铺货看起来是「采集 → 改改字段 → 发布」，实际有七个环，每一环都有静默失败的坑：

| 环 | 做什么 | 最容易踩的坑 |
|---|---|---|
| 0 采集 | 1688 列表全量 → 详情页一趟取「件重 + 运费 + 入库」 | 运费读的是默认收货地；包邮商品被误判失败 |
| 1 IP 预筛 | 主图拼长图 → 外部 VLM 判三栏 → 拦/放行清单 | 标题层永远漏；人工读图也会漏 |
| 2 认领 | 放行件 ∩ 已入库 ∩ 未认领 → 认领到平台 | 认领后写回会静默失败 |
| 3 标题 | 逐条手写三段式 → 自检 → 写回 + 回读校验 | 两个脚本吃的 JSON 格式不一样 |
| 4 七环写回 | 重量/库存/结算价/描述过滤/图片裁剪/欢迎语 | 属性表的「重量」是占位值 |
| 5 终检 | 全量逐条核对 | **只查第 1 页 200 条却报「全部通过」** |
| 6 发布 | 铺到企业名下全部店 | 写接口没有 dry-run，参数一补齐就真发布 |

外加两个横切问题：**IP 判定**（蹭牌仿品只能看图发现）和 **Token 成本**（图片占链路 token 的 85%）。

---

## 几条硬结论（都来自实测，不是理论）

**1. 人工读图 ≠ 覆盖度，VLM 全量预筛是刚需层。**
实测一批 44 件水杯，标题层黑名单 0 命中，主图 contact sheet 抓出 Hello Kitty 仿款、
史努比仿款、FROZEN 包装盒。另一批用人工读图复核，**漏掉 1 件美少女战士硬 IP 并已上架**——
是后来靠回溯筛查才抓出来的。把读图搬到外部 VLM 后，图片 token 从 ~122k 降到 ~13k。

**2. IP 判定必须四处同扫。**
`1688 原标题 + VLM 角色栏 + VLM 英文词栏 + VLM 厂牌栏`。
只扫一边会漏——实测两边各漏 2 件。**厂牌栏是 IP 的富矿**：
蹭牌仿品常把 IP 名当厂牌印，标题层和角色栏都看不出来。

**3. 匹配黑名单要用词边界，不能用子串。**
`w in text` 会让 `pony` 命中 `company`、`tom` 命中自有厂牌 `CHICU TOM`
（实测 4 件被误判）。改成词边界后回扫全量，命中列表完全一致、零新增误伤。

**4. 任何「先取列表再按 id 过滤」的逻辑必须分页取全量。**
ERP 列表接口都有分页。数据量涨过 200 条后，取第 1 页会**静默漏掉后面所有条目**——
不报错、不提示，脚本看起来正常跑完了。终检脚本曾因此只查 200 条却报「全部通过」。

**5. 写接口的入参从前端 chunk 挖，不猜。**
`publishGoods` 之类的写接口没有 dry-run：参数一补齐就立刻执行。
探参数必须用**无效 id** 或 `page.route` + `abort`。

**6. 长跑任务的 token 成本来自「读」，不是「跑」。**
逐件打印 227 行 ≈ 3,030 token——但这 3,030 token 是**读日志时进上下文**的。
数据落 JSON、stdout 只放进度、不 poll，这笔成本就是零。真实成本是时间。

**7. 长参数列表在 PowerShell 下会转义坏。**
用 `--ids-file`，不要把上百个 id 塞进命令行。

## 怎么用

**安装**：把整个目录放进你的 Agent skills 目录，例如
`<AGENT_SKILLS_DIR>/kjx-shopee-pipeline/`（各 Agent 的 skills 根目录不同，见对应文档）。

**触发**：描述里已写明触发面，比如
「上货 / 铺货 / 采集 1688 / 认领 / 改标题 / 改重量 / 改结算价 / 终检 / 轻出海 / 批次 N 波」，
以及「给这条管道加个新功能」。

**典型用法**：

```powershell
# 0 体检（零图像开销，先跑）
python scripts\kjx_status.py

# 1 IP 预筛（主图拼长图 -> 外部 VLM -> 三栏结论落盘）
python scripts\kjx_vlm_review.py --all --imgs 5
python scripts\kjx_vlm_retry.py          # 失败件必须重试，静默跳过 = 漏检
python scripts\kjx_final_list.py          # 产出拦 / 放行清单

# 2 认领（破坏性，先问用户）-> 3 标题 -> 4 七环写回 -> 5 终检 -> 6 发布
```

**设门顺序**（越便宜越先跑）：脚本体检 → 单点检查 1 件 → 每单元代表帧 contact sheet → 全量。

## ⚠️ 脱敏说明

本仓库是**公开版**，已做脱敏处理。以下内容全部替换为占位符：

| 占位符 | 含义 |
|---|---|
| `<PROJECT_ROOT>` | 你的项目根目录 |
| `<ERP_API_HOST>` / `<ERP_WEB_HOST>` | 第三方跨境 ERP 的 API / 前端域名 |
| `<MERCHANT_ID>` | 企业（多店铺主体）id |
| `<SHOP_ID>` / `<SHOP_GOODS_ID>` | 店铺 id / 店铺商品 id |
| `<你的1688账号>` / `<你的unb号>` | 1688 账号标识 |
| `<MEMBER_ID>` | 1688 店铺 memberId（mtop 列表接口用） |
| `<OFFER_ID>` / `<CLAIM_ID>` / `<BASE_ITEM_ID>` | 业务实例 id |
| `<你的货代仓所在区>` | 货运代理仓所在区域（运费计算基准地） |

**方法论、判据、坑、脚本规约都是完整的**，只有「谁家的哪个 id」被抹掉。
要落地成自己的版本，把占位符换成本机的实际值即可。

## 合规边界

- 自动化**只走第三方 ERP 自家后台**，绝不直接用 API 连平台卖家中心。
  ERP → 平台那一跳由 ERP 用用户已授权的店铺通道完成。
- 凭证不进入对话上下文、不进日志、不进记忆。
- 破坏性操作（认领 / 删除 / 发布）执行前必须拿到明确确认。
